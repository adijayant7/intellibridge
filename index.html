IntelliBridge

A low-cost, offline multi-sensor framework for real-time bridge health risk classification, from sensors and ESP32 hardware to TinyML software and a live danger level.

1. The problem

Manual inspections are intermittent

Visits catch visible damage but miss transient events and slow internal degradation between inspections. Many failures begin with small vibration shifts or micro-cracks the eye cannot see.

Cloud-only monitoring is impractical

Continuous cloud systems need steady connectivity and power, which remote or low-budget bridges rarely have. Losing the network must never disable safety actuation.

2. Hardware

ESP32 hub

Reads every sensor, runs the model in bursts, sleeps deeply between sampling campaigns and decides locally in milliseconds.

MPU6050

Three-axis accelerometer and gyroscope. Gives vibration signatures, dominant frequency and tilt.

Ultrasonic sensor

Time-of-flight distance across a joint. Tracks crack width and gap changes.

Water-level sensor

Detects rising water and scour risk. Raises risk immediately above its limits.

Strain gauge

Measures local strain and load cycles for early fatigue and load anomalies.

Temperature and humidity

Context for material effects. Temperature corrects strain, crack and frequency readings.

Servo gate and alarm

The actuator. Closes the safety gate and sounds the local alarm with no network needed.

4. Approach: from fixed thresholds to edge AI

Base paper: fixed thresholds

Hard-coded limits map each sensor to Safe, Warning or Danger. Easy to deploy, but heavy vehicles cause false alarms and slow degradation stays under the limits.

IntelliBridge: learned baseline

A compact model learns what a healthy bridge looks like, scores how far a reading is from it, and uses water level, strain and temperature as context. High scores trigger the offline safety loop, medium scores raise the sampling rate and queue a report.

5. Data, models and results

Vibration model on real LUMO data

Spectral features (24 per 60-second window) from six bridge-tower test groups, with MPU6050-like noise added. A Mahalanobis anomaly model trained on healthy windows only, tested on groups it never saw. Warning line 6.85, Danger line 9.05. Exported as a 2.3 KB C header.

Multi-sensor danger model

No public dataset has all five sensors, so this model trains on simulated readings with physics-based limits. It takes any value and returns a danger level from 1 to 100.

How the danger model works

  1. Physics step. The 8 readings become 7 “how abnormal” numbers. Temperature is subtracted from strain, crack and frequency, and a closing crack counts the same as an opening one.
  2. Isotonic regression. One learned curve per sensor turns “how abnormal” into a severity from 0 to 100. Each curve only rises, so a worse reading never looks safer.
  3. Monotonic gradient boosting. It combines the 7 severities into one danger level. The worst sensor leads, and other abnormal sensors add a smaller amount.
  4. Level to class. 1 to 29 is Safe, 30 to 64 is Warning, 65 to 100 is Danger. This page runs the same tables that are exported to the ESP32.

8. Status and next steps

Done

Real-data vibration test, multi-sensor danger model, web app and this dashboard, and the ESP32 export checked in C against the Python model.

Not yet done

The ESP32 does not yet compute the features from live MPU6050 readings. There is no real multi-sensor hardware data yet, so the danger limits are engineering assumptions.

Pilot plan: two rural bridges (Q4)

Hardware integration, 4 weeks of baseline collection, on-device model calibration and safety gate validation. Then retrain the danger model on the real readings.

Honest limits. The LUMO test uses 5 healthy and 5 damaged files per group from one tower, with simulated sensor noise. The multi-sensor model is trained on simulated data, so its accuracy figures show the method, not real-world performance.
